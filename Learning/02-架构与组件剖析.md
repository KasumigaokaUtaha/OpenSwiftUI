## 0. 一张图看懂 SwiftUI

```
             ┌────────────────────────── 宿主 ──────────────────────────┐
  事件 ───►  │ UIHostingView / NSHostingView / StdoutRendererHost       │ ──► 屏幕
             │   · 接收触摸、尺寸、环境变化                              │
             │   · 每帧调用 viewGraph.updateOutputs(at: time)            │
             │   · 把 DisplayList 交给渲染器（CALayer/UIView/RenderBox） │
             └───────────────▲──────────────────────────┬───────────────┘
                             │ DisplayList / 偏好 / 尺寸 │ setRootView / setSize /
                             │                          ▼ asyncTransaction
             ┌──────────────── ViewGraph : GraphHost ────────────────────┐
             │ 全局输入：time, environment, transaction, phase, 根视图值  │
             │ 根输出  ：rootDisplayList, rootLayoutComputer, 偏好……      │
             └───────────────▲──────────────────────────┬───────────────┘
                             │                          │ Root._makeView(view:inputs:)
             ┌──────────── 由 _makeView 递归建出来的依赖图 ───────────────┐
             │  [View 值] ─► [body 规则] ─► [子 View 值] ─► …             │
             │  [environment] ─► [ChildEnvironment] ─► …                  │
             │  [LayoutComputer] ─► [ChildGeometries] ─► [position/size]  │
             │  [叶子 DisplayList] ─► [PreferenceCombiner] ─► 根          │
             └───────────────────────────▲───────────────────────────────┘
                                         │ Attribute / Rule / Subgraph
             ┌──────────────── AttributeGraph（私有框架）─────────────────┐
             │ 节点 + 输入/输出边；推脏（propagate_dirty）、拉取求值        │
             │ （update_attribute），值比较截断（compareValues）           │
             └───────────────────────────────────────────────────────────┘
```

理解 SwiftUI 只需要抓住三件事：

1. **View 是值，不是对象**。它的作用是在 `_makeView` 时被「编译」成图中的一组节点。
2. **图负责一切增量计算**。状态改变 = 某个输入节点被写；之后只有真正受影响的节点被重新计算。
3. **输出是数据**。布局（`LayoutComputer`）、要画什么（`DisplayList`）、偏好（`PreferenceKey`）都是图节点的值，宿主读取它们。

## 2. AttributeGraph：一切的地基

### 2.1 概念

| 概念 | Swift API | 说明 |
|---|---|---|
| 图 | `Graph` | 节点存储 + 更新调度。SwiftUI 所有宿主共享一个 `GraphHost.sharedGraph`，每个宿主有自己的 context（`Graph(shared:)`）。 |
| 子图 | `Subgraph` | 节点分组 + 生命周期单位。`invalidate()` 会一次性销毁其中所有节点。分支切换、`ForEach` 删除元素、`AnyView` 类型变化都靠它。 |
| 节点 | `Attribute<Value>` / `AnyAttribute` | 一个 32 位 ID。要么是输入（`Attribute(value:)`），要么由规则计算。 |
| 规则 | `Rule`（`var value`）/ `StatefulRule`（`mutating func updateValue()`） | 节点的计算逻辑。规则本身是 struct，存放在节点内存里（「body」），可以带状态。 |
| 其他 | `WeakAttribute`、`OptionalAttribute`、`IndirectAttribute` | 弱引用、可空引用、**间接节点**（可在运行时重定向源节点，用于动态子图的输出转发） |

规则读取 `@Attribute var x` 时会调用 `AGGraphGetValue`，后者在当前更新帧上**自动登记一条输入边**。所以依赖图是「运行规则时读到谁就依赖谁」动态建出来的，不需要手写依赖声明。

### 2.2 更新算法（以 Compute 源码为准）

`Compute/Sources/ComputeCxx/Graph/Graph.cpp`、`UpdateStack.cpp`：

1. **写入**：`Graph::value_set` → 值真的变了（`compareValues`）才继续 → `mark_changed` 把所有读者的对应输入边标为 `Changed` → `propagate_dirty`：沿输出边 DFS 把下游节点标脏，遇到已脏节点剪枝（`Graph.cpp:1716`）。
2. **读取**：`Graph::update_attribute`（`Graph.cpp:1170`）——节点已初始化且不脏，直接返回 `Unchanged`；否则压入 `UpdateStack`。
3. **求值**：`UpdateStack::update()`（`UpdateStack.cpp:200`）循环：先把输入逐个推入栈更新（`push_inputs`），任何一条输入边带 `Changed` 标记就把本帧标为 `pending`；只有 `pending` 时才调用规则的 `update` 回调。主线程属性（`is_main_thread`）会切回主线程处理器执行。
4. **截断**：规则输出的新值若与旧值相等，就不标记下游输入边为 `Changed`——下游虽然被标脏，但被拉取时会发现「输入都没变」，直接清掉脏标记，不运行规则。

这就是「**推脏 + 拉取 + 值比较截断**」。它保证：一次状态修改的代价只与「真正变化的那部分」成正比。

### 2.3 `compareValues`：不要求 Equatable 的比较

SwiftUI 的 View 结构体通常不遵守 `Equatable`，图却能判断「父视图重算后，子视图的值有没有变」。秘密在 AG 的 `compareValues`：它根据 Swift 运行时元数据为类型生成比较布局（`LayoutDescriptor`）——POD 区域 `memcmp`，`Equatable` 字段调 `==`，引用比较指针，闭包等无法比较的部分视为不等。OpenAttributeGraph 中对应 `Sources/OpenAttributeGraph/Runtime/CompareValues.swift` 与 C++ 的 `Comparison/` 目录。

> 实践启示：在视图里存闭包会让该视图「永远被认为变了」；把闭包包进稳定的引用类型、或拆分子视图，可以减少不必要的 body 求值。

### 2.4 三个实现的对比

| | Apple AttributeGraph | OpenAttributeGraph | Compute | DanceUIGraph |
|---|---|---|---|---|
| 语言 | C++ + Swift | C++ + Swift | C++ + Swift（依赖 Swift 源码子模块读取元数据） | C++ / ObjC++ |
| 状态 | 私有闭源 | 研究 + 部分可用 | 较完整，OpenSwiftUI Linux 默认后端 | 生产可用（iOS） |
| 特色 | — | 与 AG API 逐一对应，有 compatibility test | 完整 `UpdateStack`、`TraceRecorder`、调试服务器 | `v4` 新图实现、KDebug tracer、`MovableLock` |

## 3. View 与 `_makeView`：把视图「编译」成图

### 3.1 View 协议（`View/View.swift`）

```swift
public protocol View {
    static func _makeView(view: _GraphValue<Self>, inputs: _ViewInputs) -> _ViewOutputs
    static func _makeViewList(view: _GraphValue<Self>, inputs: _ViewListInputs) -> _ViewListOutputs
    static func _viewListCount(inputs: _ViewListCountInputs) -> Int?
    associatedtype Body: View
    @ViewBuilder var body: Body { get }
}
```

内部再细分三种角色：

* `PrimitiveView`：`Body == Never`，自己实现 `_makeView`（Text、Color、ModifiedContent、各种 Stack）。
* `UnaryView`：在列表中只占一个位置（`_makeViewList` → `unaryViewList`）。
* `MultiView`：多元视图（TupleView、ForEach）；单独作为视图使用时 `makeImplicitRoot` 包一层隐式 VStack。

### 3.2 自定义视图的默认 `_makeView`（`View/CustomView.swift`）

```swift
nonisolated package static func makeView(view: _GraphValue<Self>, inputs: _ViewInputs) -> _ViewOutputs {
    let fields = DynamicPropertyCache.fields(of: Self.self)        // 扫描 @State 等字段
    var inputs = inputs
    let (body, buffer) = makeBody(view: view, inputs: &inputs.base, fields: fields)
    ...
    let outputs = Body.makeDebuggableView(view: body, inputs: inputs) // 递归
    return outputs
}
```

`makeBody` 由 `BodyAccessor.makeBody` 实现（`Data/DynamicProperty/DynamicProperty.swift`）：

* 没有 DynamicProperty → 建 `StaticBody`（无状态 `StatefulRule`，`updateValue` 里直接 `container.body`）；
* 有 → 建 `DynamicBody`，持有 `_DynamicPropertyBuffer`：

```swift
mutating func updateValue() {
    if resetSeed != phase.resetSeed { links.reset(); resetSeed = phase.resetSeed }
    var (container, changed) = $container.changedValue()
    withObservation {
        withUnsafeMutablePointer(to: &container) {
            if links.update(container: $0, phase: phase) { changed = true }   // 注入状态
        }
        accessor.updateBody(of: container,
                            changed: changed || !hasValue || AnyAttribute.currentWasModified)
    }
}
```

`ViewBodyAccessor.updateBody` 只在 `changed` 时才 `setBody { container.body }`——**这就是「body 何时被调用」的全部答案**：视图值变了、或它的某个动态属性报告变化、或首次求值。

DanceUI 的同名实现在 `Internal/BodyAccessing/{StaticBody,DynamicBody,ViewBodyAccessor}.swift`，`UIElements/View/View.swift` 的 `makeView` 与上面几乎一致。

### 3.3 `_GraphInputs` / `_ViewInputs` / `_ViewOutputs`

`Graph/GraphInputs.swift`、`View/Input/ViewInputs.swift`、`View/Input/ViewOutputs.swift`：

| 结构 | 主要字段 | 说明 |
|---|---|---|
| `_GraphInputs` | `time`、`environment`（经 `cachedEnvironment`）、`phase`、`transaction`、`customInputs: PropertyList`、`options`、`mergedInputs` | 与视图无关的通用输入。`customInputs` 是一个 PropertyList，任意模块都能往里塞自定义输入（`GraphInput` 协议），这是 SwiftUI 扩展性的关键。 |
| `_ViewInputs` | `base`、`preferences: PreferencesInputs`、`transform`、`position`、`containerPosition`、`size`、`safeAreaInsets`、`containerSize` | 视图专属输入：几何、要求的偏好键。`requestsLayoutComputer`/`needsGeometry` 等选项控制按需生成。 |
| `_ViewOutputs` | `preferences: PreferencesOutputs`、`layoutComputer` | 输出就两样：**偏好** 和 **布局计算器**。 |

修饰符改写 inputs 影响子树，改写 outputs 影响祖先——这是所有修饰符的统一模型。

### 3.4 `ViewGraph`：根（`View/Graph/ViewGraph.swift`）

* 字段：几十个根级 `@Attribute`——`rootTransform`、`zeroPoint`、`proposedSize`、`safeAreaInsets`、`rootGeometry`、`position`、`dimensions`、手势相关、`defaultLayoutComputer`，以及弱引用的 `rootResponders`、`rootLayoutComputer`、`rootDisplayList`。
* `instantiateOutputs()`（第 261 行）：在 `rootSubgraph` 中构造 `_ViewInputs`，按 `requestedOutputs` 打开 layout/displayList 等需求，让各 `ViewGraphFeature` 修改 inputs，然后 `makeRootView(rootView, inputs)`（外面包了一层 `_SafeAreaInsetsModifier`），最后把 `outputs.layoutComputer` 回填给 `RootGeometry`、把 `outputs.preferences.displayList` 包成 `RootDisplayList`。
* `updateOutputs(async:)`（第 512 行）：`repeat { instantiateIfNeeded; startTransactionUpdate; finishTransactionUpdate; updatePreferences; features… } while needsTransaction && counter != 8`——最多循环 8 次，处理更新过程中又产生的事务；结束后在主线程通知 `preferencesDidChange`、feature 更新、`sizeThatFits` 观察者。

### 3.5 `GraphHost`：事务与全局输入（`Graph/GraphHost.swift`）

* `GraphHost.Data`（第 56 行）：`graph`、`globalSubgraph`、`rootSubgraph`、`time`、`environment`、`phase`、`hostPreferenceKeys`、`transaction`、`updateSeed`、`transactionSeed`、`inputs`。
* `asyncTransaction(_:id:mutation:style:)`（第 426 行）：把一个 `GraphMutation` 排进 `pendingTransactions`；同一 `Transaction.ID` 且可合并（`mayConcatenate`）的修改会合并到上一个事务；第一次排队时调用 `graphDelegate?.beginTransaction()` 通知宿主「需要更新」。
* `flushTransactions()`（第 533 行）：对每个待处理事务 `runTransaction(transaction) { withTransaction(transaction) { mutations.apply() } }`，然后 `graphDelegate?.graphDidChange()`。
* `runTransaction`：设置 `data.transaction` → `startTransactionUpdate`（`transactionSeed += 1`）→ 执行修改 → `finishTransactionUpdate`（在全局子图里更新所有「事务性」节点，再执行 continuation）→ 清空 transaction。

DanceUI：`Internal/Graph/GraphHost.swift`（861 行，`asyncTransaction` 在第 495 行），结构一致。

## 4. 数据流：State / Binding / DynamicProperty

### 4.1 DynamicProperty 机制

* `DynamicPropertyCache.fields(of:)`：用运行时元数据遍历类型字段（struct、enum 的每个 case），记录每个 `DynamicProperty` 字段的类型、**字节偏移**和名字，并缓存；同时汇总 `_propertyBehaviors`（如 `allowsAsync`）。
* `_DynamicPropertyBuffer`（`Data/DynamicProperty/DynamicPropertyBuffer.swift`）：一块异构缓冲区，按字段顺序存放各属性的 `DynamicPropertyBox`；`update(container:phase:)` 时按偏移把每个盒子作用到视图结构体内存上。
* 每个属性包装器实现 `static func _makeProperty(in:container:fieldOffset:inputs:)`，向 buffer 追加自己的盒子；默认实现会递归扫描嵌套的 DynamicProperty（所以自定义属性包装器里包 `@State` 也能工作）。

### 4.2 State（`Data/State/State.swift`、`StoredLocation.swift`）

```swift
public static func _makeProperty<V>(in buffer: inout _DynamicPropertyBuffer, container: _GraphValue<V>,
                                    fieldOffset: Int, inputs: inout _GraphInputs) {
    let attribute = Attribute(value: ())                          // 「信号」节点
    let box = StatePropertyBox<Value>(signal: WeakAttribute(attribute))
    buffer.append(box, fieldOffset: fieldOffset)
    addTreeValue(attribute, as: Value.self, at: fieldOffset, in: V.self, flags: .stateSignal)
}
```

```swift
mutating func update(property: inout State<Value>, phase: _GraphInputs.Phase) -> Bool {
    let oldLocation = location
    var changed = oldLocation == nil
    let newLocation = oldLocation ?? (property._location as? StoredLocation
                         ?? StoredLocation(initialValue: property._value, host: .currentHost, signal: signal))
    location = newLocation
    let signalChanged = signal.changedValue()?.changed ?? false
    property._value = newLocation.updateValue          // 注入本帧的值
    property._location = newLocation
    if signalChanged { changed = oldLocation == nil || newLocation.wasRead }
    return changed
}
```

写入路径 `StoredLocationBase.set(_:transaction:)`：

1. 若正在图更新中（`isUpdating`）→ 打印「Modifying state during view update」并忽略；
2. `compareValues` 判断值是否真变，变了就更新 `currentValue`；
3. 捕获 `transaction.current` 与 `Transaction.id`，在主线程上 `host.asyncTransaction(transaction, id:, mutation: BeginUpdate(box: self))`；
4. 事务执行时 `BeginUpdate.apply()`：`updateValue = currentValue`，并 `$signal.invalidateValue()` → 推脏到读过它的 body。

几个值得记住的细节：

* **`currentValue` vs `updateValue`**：在动作闭包里写完立刻读，读到的是 `currentValue`（新值）；而 body 读到的是本帧注入的 `updateValue`。保证一次更新内部看到的状态一致。
* **`wasRead` 优化**：body 从没读过的 State 变化不会触发 body 重算。
* **`ObservableLocation`**（同文件）支持多个宿主观察同一个位置（`@Observable` 对象、`Bindable` 等）。

DanceUI：`AppStructure/State/StatePropertyBox.swift`，逻辑一致，只多了 `Trace.emitEvent` 埋点。

### 4.3 Binding（`Data/Binding/*.swift`）

`Binding` = `transaction` + `location: AnyLocation<Value>`（+ 缓存的 `_value`）。`$state.field` 通过 `Projection`（`ProjectedLocation`）派生子位置，`LocationBox` 缓存投影结果以保证同一路径得到同一个对象（比较时可以短路）。`BindingOperations` 实现了 `?? default`、`Optional` 解包等派生绑定。

## 5. Environment 与 Preference：一下一上两条数据流

### 5.1 EnvironmentValues（`Data/Environment/*.swift`、`Data/Util/PropertyList.swift`）

* `EnvironmentValues` 包装一个 `PropertyList`：**不可变单向链表**，写入 = 在表头前插新元素；比较 = 比较表头指针。附带 `PropertyList.Tracker` 用于记录「某次读取用到了哪些 key」。
* `.environment(\.k, v)` → `_EnvironmentKeyWritingModifier._makeInputs`：用 `ChildEnvironment` 规则替换 `inputs.environment`。`ChildEnvironment.updateValue` 在「父环境未变且修饰值未变」时保留旧值，避免整棵子树失效。
* `@Environment` 的盒子 `EnvironmentBox`（`Environment.swift:310`）：环境变化时重新取 keyPath 的值，**与旧值相等就不报告变化**——所以环境里无关 key 的变化不会让你的 body 重算。
* `CachedEnvironment`（`Data/Environment/CachedEnvironment.swift`）：对「从环境派生出来的值」按 ID 缓存派生节点（`attribute(id:_:)`），还缓存解析后的 ShapeStyle（`resolvedShapeStyles`）、动画帧（`animatedFrame`）等，避免每个视图各建一份。

### 5.2 Preference（`Data/Preference/*.swift`）

* 祖先在 `inputs.preferences` 中声明需要哪些 key（`PreferenceKeys`）；不被需要的偏好根本不会被创建。
* 子视图在 `outputs.preferences`（`PreferencesOutputs`，一个 `[KeyValue]` 小数组）中放对应节点。
* 多孩子容器用 `PreferenceCombiner` 依次 `reduce` 合并。
* **显示列表本身就是一种偏好**：`PreferencesOutputs` 的 setter 里专门判断 `if key == DisplayList.Key.self`。
* `HostPreferencesKey` 把需要交给宿主的偏好（如导航标题）打包上浮；`PreferenceBridge` 处理跨宿主（如 UIKit 内嵌 SwiftUI）的偏好传递。

## 6. 布局

### 6.1 LayoutComputer（`Layout/LayoutComputer/LayoutComputer.swift`）

`LayoutComputer` 是图中流动的布局值：内部是 `AnyLayoutEngineBox`（引擎 + 尺寸缓存）和一个 seed；比较时只比较 seed。接口：

```swift
func sizeThatFits(_ proposedSize: _ProposedSize) -> CGSize
func lengthThatFits(_ proposal: _ProposedSize, in direction: Axis) -> CGFloat
func childGeometries(at parentSize: ViewSize, origin: CGPoint) -> [ViewGeometry]
func explicitAlignment(_ k: AlignmentKey, at viewSize: ViewSize) -> CGFloat?
func spacing() -> Spacing
```

`StatefulRule.updateLayoutComputer(...)` 只在引擎（含其参数）变化时换一个新 seed。

### 6.2 容器如何连接孩子（`Layout/LayoutView.swift`，`Layout.makeStaticView`）

```swift
layoutComputer = Attribute(StaticLayoutComputer(layout: root.value, environment: inputs.environment, childAttributes: []))
geometry = Attribute(LayoutChildGeometries(parentSize: inputs.size, parentPosition: inputs.position,
                                           layoutComputer: layoutComputer))
list.makeAllElements(inputs: inputs) { inputs, makeElement in
    let childGeometry = Attribute(LayoutChildGeometry(childGeometries: geometry, index: index))
    inputs.position = childGeometry.origin()
    inputs.size = childGeometry.size()
    let outputs = makeElement(inputs)
    childAttributes.append(LayoutProxyAttributes(layoutComputer: .init(outputs.layoutComputer), …))
}
layoutComputer.mutateBody(as: StaticLayoutComputer<Self>.self, invalidating: true) {
    $0.childAttributes = childAttributes          // 先建父、再建子、最后回填
}
```

依赖关系形成一个「环形但不成环」的结构：父 LayoutComputer ← 孩子 LayoutComputer；孩子 position/size ← 父 ChildGeometries ← 父 LayoutComputer + 父 size/position。值的流向是单向的，所以没有循环依赖。

* 一元布局（padding、frame、aspectRatio、offset……）走 `UnaryLayout`（同文件第 13 行）：`sizeThatFits(in:context:child:)` + `placement(of:in:)`。
* 公开的 `Layout` 协议（iOS 16）通过 `LayoutProxy`/`LayoutSubviews` 与同一套 `LayoutComputer` 对接；`HStack/VStack` 内部就是 `_HStackLayout/_VStackLayout`，算法在 `Layout/Stack/StackLayout.swift`（按弹性从小到大分配剩余空间，支持 `layoutPriority`）。
* `count == 1 && isIdentityUnaryLayout` 时直接透传孩子，省掉一层节点（`67fa0855` 修过这里的 bug）。

DanceUI：`Internal/Layout/` 下的 `LayoutComputer.swift`、`UnaryLayoutEngine.swift`、`RootGeometry.swift`、`LayoutProxy*.swift` 等一一对应。

## 7. ViewList 与 ForEach

### 7.1 `_ViewListOutputs`（`View/Input/ViewList.swift`）

```swift
public struct _ViewListOutputs {
    package enum Views {
        case staticList(any ViewList.Elements)                     // 构建期已知
        case dynamicList(Attribute<any ViewList>, ListModifier?)    // 运行期才知道
    }
    package var views: Views
    package var nextImplicitID: Int
    package var staticCount: Int?
}
```

* `ViewList` 协议：`count(style:)`、`applyNodes(from:style:list:transform:to:)`、`edit(forID:since:)`、`firstOffset(forID:style:)`、`traits`……支持懒加载（`List`/`LazyVStack` 只实例化可见元素）、分组（`Section`）、编辑动画。
* `_ViewList_ID`：每个元素的身份 = 「显式 ID（ForEach 给的）」+「隐式 ID（在 TupleView 中的位置）」的组合，`ID.Canonical` 用于比较。
* `_viewListCount(inputs:)`：静态地问「你会产生几个元素」，`nil` 表示动态。

### 7.2 ForEach（`View/DynamicViewContent/ForEach.swift`）

`ForEachState`（第 333 行）是核心：它持有 `items: [ID: Item]`、`edits`、`lastTransaction`、驱逐（eviction）相关状态等，每个 Item 对应一个子 `Subgraph`；数据变化时按 ID diff，复用已有的子图、为新 ID 建子图、销毁消失的 ID，并产出 `ForEachList: ViewList`。这就是「显式身份」：**状态跟着 ID 走，而不是跟着位置走**。

### 7.3 DynamicContainer（`Layout/Dynamic/*.swift`）

动态列表在布局容器中由 `DynamicContainer` + `DynamicLayoutMap` 管理：按 ID 维护子视图条目、处理插入/删除过渡（transition）、把每个条目的 `layoutComputer` 汇总给容器的 `DynamicLayoutComputer`。

### 7.4 结构化身份：`_ConditionalContent` / `AnyView`（`View/ConditionalContent.swift`、`View/DynamicView/*.swift`）

```swift
package mutating func updateValue() {          // _ConditionalContent.Container
    let content = content
    guard hasValue, value.matches(content) else {
        if hasValue { eraseInfo(value) }        // subgraph.willInvalidate + invalidate
        value = makeInfo(content)               // 新建子图，在里面 makeTrueOutputs/makeFalseOutputs
        return
    }
    var info = value; info.content = content; value = info
}
```

分支不变时只更新内容；分支一变，整棵旧子树（连同 `@State`）销毁。`provider.attachOutputs(to:)` 把新子图的输出接到父视图持有的 **IndirectAttribute** 上，父视图看到的输出节点 ID 永远不变。`AnyView` 同理，只是「身份」换成了底层类型（`DynamicView` 协议 + `DynamicViewContainer`）。

## 8. Transaction 与动画

* `Transaction`（`Animation/Transaction/Transaction.swift`）同样是 PropertyList，常用 key：`animation`、`disablesAnimations`、`tracksVelocity`、`animationListener`……`withTransaction`/`withAnimation` 设置线程局部的当前事务，State 的 setter 把它捕获进 `asyncTransaction`。
* 每个可动画修饰符在 `_makeView` 中把自己的值包进 `AnimatableAttribute`（`Animation/Animatable/AnimatableAttribute.swift`）：
  * 有 `source`、`environment` 以及 `AnimatableAttributeHelper`（持有 `phase`、`time`、`transaction`、`previousModelData`、`animatorState`）；
  * `helper.update(...)`：`checkReset()` → `updateAnimatorStateIfNeeded`（源值变化且事务带动画时，创建/合并 `AnimatorState`）→ `updateValueIfNeeded`（按 `time` 采样插值），并通过 `ViewGraph.nextUpdate` 预约下一帧。
* `Animation` 本身是 `CustomAnimation` 协议的盒子：`BezierAnimation`、`SpringAnimation`/`FluidSpringAnimation`（`Spring/` 目录里有 mass-stiffness-damping、response-damping 等多套参数化）、`RepeatAnimation`、`DelayAnimation`、`SpeedAnimation`、`DefaultCombiningAnimation`（中途改目标时的叠加）。
* 过渡（`Animation/Transition/*`）：插入/删除时对子视图施加 `_ViewModifier` 序列，由 DynamicContainer 驱动。

## 9. 渲染：DisplayList

### 9.1 数据结构（`Render/DisplayList/DisplayList.swift`）

```swift
package struct DisplayList { package var items: [Item]; package var features: Features }
package struct Item { var frame: CGRect; var version: Version; var value: Value; var identity: Identity }
enum Value  { case empty; case content(Content); case effect(Effect, DisplayList); case states([(StrongHash, DisplayList)]) }
enum Content.Value { backdrop, color, chameleonColor, image, shape(Path, Paint, FillStyle), shadow,
                     platformView, platformLayer, text, flattened, drawing(ORBDisplayListContents), view, placeholder }
```

* 叶子视图（`RendererLeafView`、Color、Image、Text、Shape）产生 `content` 项；修饰符（opacity、clip、blur、geometry effect、compositingGroup……）把孩子的列表包进 `effect` 项（`Render/RendererEffect/*`、`Render/GeometryEffect/*`）。
* `Version` 是单调递增的版本号，`identity` 是稳定身份，渲染器据此做增量更新与平台对象复用。

### 9.2 后端

* `DisplayList.ViewUpdater`（`Render/DisplayList/DisplayListViewUpdater.swift`）：把显示列表增量同步到 `UIView/CALayer` 树（`ViewCache` 按 identity 复用）。
* `DisplayList.GraphicsRenderer`：用 RenderBox 直接绘制（`drawingGroup`、异步渲染、`CAHostingLayer`）。
* `DisplayListStdoutRenderer` / `StdoutRendererHost`：**Linux 上把显示列表打印到终端**（`66235c05` 引入，`eaced492` 起在 Linux CI 运行）。
* `DisplayListPrinter`：S 表达式格式打印，与真 SwiftUI 的 `SWIFTUI_PRINT_TREE` 输出对齐，便于对照调试。

DanceUI：`Internal/Display/`（`DisplayList.swift`、`DisplayListViewUpdater.swift`、`DisplayListViewCache.swift`、`RenderBoxWarpper.swift`……），只有 UIKit 后端。
