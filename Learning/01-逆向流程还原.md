## 1. 一句话总结

OpenSwiftUI 的作者（Kyle-Ye）走的是一条「**先抄接口、再接真引擎、自底向上补实现、用真 SwiftUI 当对照组验证**」的路线：

1. 以 SDK 中公开的 `SwiftUI.swiftinterface` 为 API 规格书，先写出类型「外壳」；
2. 从模拟器运行时里提取 **私有框架 AttributeGraph** 的二进制，伪造 `.xcframework` 并手写头文件，让自己的代码能链接、调用真正的 AG；
3. 用 Hopper 反汇编 SwiftUI / AttributeGraph 二进制，用 `swift-reflection-dump` 导出类型字段布局，逐个文件「翻译」回 Swift；
4. 从底层数据结构（`VectorArithmetic`、`PropertyList`、`BloomFilter`、`Location`……）开始，一层层往上实现到 `GraphHost`、`ViewGraph`、布局、动画、渲染；
5. 同时搭建 **兼容性测试**：同一份测试代码分别链接 SwiftUI 和 OpenSwiftUI 运行，结果必须一致；后来又加入「直接调用 SwiftUI 私有符号」的 Dual Test 和与真 SwiftUI 截图对比的 UI 测试；
6. 把对 AttributeGraph 的逆向独立成单独项目（OpenGraph → OpenAttributeGraph），并在 Linux 上用开源实现替换私有框架。

## 3. 逆向工作流，逐步拆解

### 3.1 API 规格：`.swiftinterface` 与 `.tbd`

早期的 `Development.md`（`71d30a8a`、`ab155c51` 版本）把「需要的文件」列得很清楚：

| 类别 | 路径 |
|---|---|
| SwiftUI 接口 | `…/iPhoneOS.sdk/System/Library/Frameworks/SwiftUI.framework/Modules/SwiftUI.swiftmodule/arm64-apple-ios.swiftinterface` |
| SwiftUI 二进制 | `…/iOS 15.5.simruntime/…/System/Library/Frameworks/SwiftUI.framework/SwiftUI`（以及 iOS 17.0 的同一路径） |
| AG 的 tbd | `…/iPhoneSimulator.sdk/System/Library/PrivateFrameworks/AttributeGraph.framework/AttributeGraph.tbd` |
| AG 二进制 | `…/iOS 15.5.simruntime/…/PrivateFrameworks/AttributeGraph.framework/AttributeGraph` |

并提示「没有对应 SDK 时可以从 `xybp888/iOS-SDKs` 下载 swiftinterface/tbd」。

* **`.swiftinterface`** 给出所有 `public` 和 `@_spi` 声明的完整签名，包括 `_makeView`、`_ViewInputs` 这类带下划线的「公开但不文档化」API、`@frozen` 结构体的**存储属性布局**、`@inlinable` 函数体。这就是 OpenSwiftUI 的 API 规格书——所以 `State` 一开始就写对了 `_value` / `_location` 两个字段（`4486c395`）。
* **`.tbd`** 是链接用的「文本桩」，列出了二进制导出的**所有符号名**（含私有类型的 mangled 名），可以用 `swift-demangle` 还原。仓库里的 `Scripts/demangle.sh` + `Scripts/demangle.txt` 就是批量解码这些符号的小工具。

### 3.2 二进制：Hopper + reflection dump + 汇编手册

同一份 `Development.md` 的「Tools」一节：

```
- Hopper Disassembler      — Analyze binary of SwiftUI and AttributeGraph
- swift-reflection-dump    — Produce swiftui-reflection-dump.txt to simplify our work
                             (see https://gist.github.com/ole/7a08561a4258bd2f82a92bc21a7b2355)
- ARM Instruction Reference
```

* **Hopper** 反汇编 / 生成伪代码，用来读函数实现。
* **swift-reflection-dump** 读取二进制中的 Swift 反射元数据（`__swift5_fieldmd` 等段），导出**每个类型（包括私有类型）的字段名和类型**。这一步极其关键：SwiftUI 内部类型（`StatePropertyBox`、`DynamicBody`、`ViewGraph` 的几十个 `@Attribute` 字段）的名字和顺序，都是从这里来的。今天 `ViewGraph.swift` 里那一长串 `@Attribute var rootTransform`、`@OptionalAttribute var containerSize`……就是这份 dump 的「翻译」。
* 因为当时主要分析模拟器上的 arm64 二进制，所以需要 ARM 指令手册。

### 3.3 让代码跑在真 AttributeGraph 上

AttributeGraph 是私有框架，SDK 里没有它的头文件，也不允许直接链接。项目的做法演化了三次：

1. `a96d6ddd`：在 `Sources/AttributeGraph/include/AGAttribute.h` 手写最小头文件。
2. `71d30a8a`「Add fake AttributeGraph.xcframework」：把 iOS 15.5 模拟器和 macOS 上的 `AttributeGraph` 二进制直接放进仓库，配上手写的 `AttributeGraph-Swift.h`（524 行）和 `swiftinterface`（声明 `Attribute<Value>` 等），组装成一个「假的」xcframework。
3. `7291a4db`（#21）「Use XCFramework and tbd to fix iOS private framework issue」：不再提交二进制，而是用 **tbd 桩 + 头文件** 组成 xcframework，只解决「链接」问题，运行时由系统加载真框架。这套做法后来独立成 `OpenSwiftUIProject/DarwinPrivateFrameworks` 仓库（AG、RenderBox、CoreUI 等都在里面）。

有了这一步，就可以「**用真 AG 跑自己写的 SwiftUI 上层代码**」，把问题拆成两半：上层逻辑对不对、AG 实现对不对。

### 3.4 独立逆向 AttributeGraph：OpenGraph → OpenAttributeGraph（+ Compute）

* `ab86c3df`（2023-09-25）开始写 C++ 版 `_OpenGraph`；`08b53ca8` 加入 `Rule`、`_AttributeBody`、`OGAttributeTypeFlags`；`eb5055f3` 加入 AG 测试。
* `3ea3e37b`（#11，2023-12-30）把 OG 拆为独立仓库 **OpenGraph**，OpenSwiftUI 通过 `OpenGraphShims` 选择后端：Apple 平台默认用私有 AG，其他平台用 OpenGraph。
* `20675323`（#483，2025-08-30）更名为 **OpenAttributeGraph**（以及 OpenRenderBox）。
* `289f8060`（#800，2026-02-26）加入 **Compute** 后端：James Moschou 独立完成的另一个 AG 重实现（README 致谢了 OpenSwiftUIProject 提供的「对 AttributeGraph 和 Swift 运行时的洞察」）。现在 Linux 上 stdout 示例就是跑在 Compute 上的（README：*The Linux stdout example uses the Compute backend*）。

### 3.5 一个文件一个文件地「审计」

OpenSwiftUI 每个源文件的头部都是这种格式：

```swift
//  GraphHost.swift
//  OpenSwiftUICore
//
//  Audited for 6.5.4
//  Status: Complete (Blocked by TraceRecorder)
//  ID: 30C09FF16BC95EC5173809B57186CAC3 (SwiftUI)
//  ID: F9F204BD2F8DB167A76F17F3FB1B3335 (SwiftUICore)
```

* **`ID:`** 是一个 32 位十六进制串，每个原始 SwiftUI 源文件一个。我的判断（未在仓库文档中找到明确说明）：它对应 Swift 私有声明 mangled 名中的 *file discriminator*（`P33_` 后面那 32 个字符，由源文件名哈希得到）。因为同一个源文件里的 `private`/`fileprivate` 符号共享这个串，逆向者就能把二进制里的私有符号**按原始源文件分组**，从而决定「这些类型和函数应该放在同一个 .swift 文件里」。iOS 18 之后同一个逻辑文件同时存在于 SwiftUI 和 SwiftUICore，所以有两个 ID。
* **`Audited for`** 记录这个文件对照的是哪个版本的二进制。`Docs/Version.md` 给出了映射：`3.5.2 ↔ iOS 15.5`、`5.4.38 ↔ iOS 17.4`、`6.0.87 ↔ iOS 18.0`、`6.5.4 ↔ iOS 18.5`。演化过程：`Lastest Version: iOS 15.5`（2023）→ `Audited for RELEASE_2021`（`abbf4d61`，2024-02）→ `Audited for 6.0.87` → `Audited for 6.5.4`。当前统计：970 个文件审计到 6.5.4，145 个停在 6.0.87。
* **`Status`** 记录完成度。当前 1016 个 `Complete`、120 个 `WIP`。`Docs/Status.md` 后来扩展为二维：API 覆盖度（Empty/Partial/Blocked/Complete）× 验证等级（**Verified**：与参考二进制核对过；**Generated**：自动生成、待核对；**Stubbed**：占位）。「Generated」这一级很可能对应后期引入的 AI 辅助生成（仓库里有 `AGENTS.md`/`CLAUDE.md`，见 `a8b4397b`），于是「是否与二进制核对过」被单独作为一个质量维度。
* 同一类型在不同 OS 版本里的差异用编译条件隔离：早期是 `OPENSWIFTUI_RELEASE_2021/2023/2024` 宏（`f4d379f6` #97），现在是 `OPENSWIFTUI_SUPPORT_2025_API` 之类的特性开关 + `@available(OpenSwiftUI_v6_0, *)` 自定义可用性。

### 3.7 理解是如何逐步加深的：三个例子

**State**

* `4486c395`（2023-11-02）：`State` 只有 `_value` / `_location` 和一个「TODO」的 `_makeProperty`；`DynamicProperty` 的默认实现全是空的。字段布局来自 swiftinterface，行为还没搞清楚。
* `4fc9c17f`→`85e1185a`（11 月）：先补 `Location`/`Binding`，因为 State 的 projectedValue 依赖它们。
* `75db3fa9`(#28) / `499da600`(#30) / `72be1771`(#31)（2024-01~02）：`DynamicPropertyCache` 和 `DynamicProperty` 的真正机制——字段扫描、`_DynamicPropertyBuffer`、`StaticBody`/`DynamicBody`。
* `ff01ac16`(#524) / `0c2a7882`(#535)（2025-10）：按 6.5.4 重新审计 DynamicProperty 与 DynamicPropertyBuffer，至今 `State.swift` 标注 `Audited for 6.5.4 / Complete`。

**GraphHost / ViewGraph**

* `02d8ca49`(#44, 2024-03) 第一次落地 `GraphHost`；`14597bbd`(#58) `ViewGraph`；`e449dd24`(#74) 修正 `setTime` 的一个判断写反了——说明当时是对着汇编逐条翻译的。
* `e38a0f8e`(#132)、`fb084bbc`(#175)、`bbf40ef6`(#179) 随 iOS 18 更新；`6b51798e`(#201) 补 `transaction`；`68b782a0`(#675) 修 `continueTransaction`；`4c855cf6`(#697) 补 `NextUpdate`。

**ViewList**

* `e16ee454`(#90, 2024-05) 首次加入 `ViewList` / `ViewTrait`；
* 2025-02-05 ~ 02-10 连续 12 个提交（`89018a55` … `81a9c282`）逐个类型重写 `ViewList.ID`、`Node`、`Group`、`Section`、`Elements`、`BaseViewList`；
* 2025-06 ~ 10 再补 `_ViewListOutputs.concat`(#331)、`ModifiedViewList`(#565)、`DynamicLayoutMap` 修复(#580/#625/#674)。

可以看出一个模式：**先建占位文件 → 根据 dump 填字段和签名 → 根据汇编补实现 → 用对照测试修 bug → 随新 OS 版本重新审计**。

## 4. 可复用的「逆向 SwiftUI」方法清单

把上面的过程抽象出来，如果你想自己研究某个 SwiftUI 组件：

1. **定版本**：选一个具体的 OS 版本（例如 iOS 18.5 模拟器），从 `…/Runtimes/iOS 18.5.simruntime/…/SwiftUICore.framework` 取二进制。
2. **看接口**：在 SDK 的 `SwiftUICore.swiftinterface` 里搜目标类型，拿到公开 / `@_spi` 签名和 `@frozen` 布局。
3. **列符号**：用 `nm`/`.tbd` + `swift-demangle` 列出相关的私有符号；按 `P33_xxx` 文件标识分组。
4. **导字段**：`swift-reflection-dump`（或现代的 `swift-inspect`/`ipsw` 等工具）导出私有类型的字段。
5. **读实现**：Hopper / IDA / Ghidra 读函数体；对照 OpenSwiftUI 已有的实现事半功倍。
6. **调试观察**：`SWIFTUI_PRINT_TREE=1`、`AG_DEBUG_SERVER`、LLDB 断点在 `_makeView` / `updateValue` 上，看图怎么建、怎么更新。
7. **对照验证**：写 compatibility test，同时链接 SwiftUI 与你的实现运行。

## 5. DanceUI：从代码反推它的来历

DanceUI（字节跳动开源，Apache-2.0）没有可用的开发历史，但代码本身透露了很多：

* **与 SwiftUI 内部命名高度一致**：`StatePropertyBox`、`StoredLocation`、`GraphHost.Data`（`graph / globalSubgraph / rootSubgraph / isRemoved / isHiddenForReuse / @Attribute time / environment / phase / hostPreferenceKeys / transaction`）、`DynamicBody`/`StaticBody`/`BodyAccessor`、`_GraphInputs.Phase`……这些都不是公开 API，只能来自对 SwiftUI 二进制的逆向（与 OpenSwiftUI 的 `GraphHost.swift` 第 56–118 行逐字段对照几乎一样）。见 `Sources/DanceUI/Internal/Graph/GraphHost.swift`、`Sources/DanceUI/AppStructure/State/StatePropertyBox.swift`。
* **自研 AttributeGraph**：`bytedance/DanceUIGraph` 是一个 C++ 实现，`DGGraphRef`/`DGSubgraphRef` 对应 `AGGraphRef`/`AGSubgraphRef`，头文件（`DanceUIGraphAttribute.h`、`DanceUIGraphWeakAttribute.h`、`DanceUISubgraph.h`、`DanceUIGraphTupleType.h`……）与 AG 的 C API 一一对应，并且有 `Graph/v4/` 一整套新版实现。`bytedance/DanceUIRuntime` 则承担 Swift 运行时元数据（字段、元组布局、值比较）——相当于 OpenAttributeGraph 中 `Runtime/` 那一层。
* **目标不同**：最低 iOS 13（源码中 `iOS 13.0` 出现约 3800 处，几乎每个声明都有 `@available(iOS 13.0, *)`），走 CocoaPods，面向线上 App 而非研究；`Scripts/gen_reexporter.sh` 会拿 DanceUI 的 swiftinterface 与 SwiftUI 的 swiftinterface 比对（`interface_parser export --reference-interface`）自动生成 `Reexporter.swift`，即「API 覆盖率」驱动；大量 `Trace.emitEvent(...)` 埋点、`PerformanceEngineering/` 基准测试、`utils/FeatureToggle/features.yml` 灰度开关（如 `enableCollectionViewAsyncApplyData`），以及 `DanceUICompose`、`DanceUIObservation`（Observation 宏的回移植）等扩展模块，都是工程落地的痕迹。

推断：DanceUI 同样是基于 SwiftUI 二进制逆向得到的实现（大致对应 iOS 15~16 时代的 SwiftUI 内部结构，并补了部分 iOS 17/18 API），只是开发在内部完成、开源时一次性导出。
